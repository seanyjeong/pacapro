# 학생 보호자 전화번호 릴리스 4.0.53

버전은 `4.0.53`, 갱신일은 `2026-09-29`다. `package.json`,
`package-lock.json`, `src/constants/release.json`을 함께 갱신했고 의존성,
스크립트, 잠금 파일의 패키지 해석은 변경하지 않았다.

사용자가 운영 DB 변경, 백엔드 배포, 프론트 버전업·Git 푸시를 명시적으로
승인했다. 적용 기준은 [DEPLOYMENT.md](../DEPLOYMENT.md)의 이번 보호자
전화번호 추가 릴리스 전용 점검이며, 기존 Vultr `paca` 원본을 사용한다.

Git 기준 커밋은 `0e2f656cb87b10e1149394aee1aa1109f4a0b201`이다.
적용 전 원격 `main`과 같은 커밋임을 확인하고
`rollback/v4.0.53-before-parent-phones` 태그를 만들었다.
Vercel `pacapro`가 `seanyjeong/pacapro`의 `main`에 연결된 것도 확인했다.

실제 배포 상태, 새 커밋, Vercel 배포 ID 및 검증 결과는 저장소의 비공개 운영
증빙 `docs/private/student-parent-phones-deployment-20260929.json`에 기록한다.
이 문서의 절차만으로 프론트 배포 완료를 주장하지 않는다.

## 2026-09-29 검증

- 전체 백엔드 Jest: 136개 스위트, 1,167개 테스트 통과. 소켓을 지정해야
  실행되는 MySQL 스위트 2개(14개 테스트)는 이 명령에서 생략된다.
- 이번 보호자 기능의 별도 격리 네이티브 MySQL: 7개 통합 테스트 통과,
  생략 0개. 재실행 가능한 DDL, 실제 HTTP 저장·재조회, 부분 수정·삭제,
  기존 대표 번호 보존, 학원 경계와 쓰기 권한을 검증했다.
- 실제 변경 내용에 대한 릴리스 메타데이터 검증 및 메타데이터 테스트
  15개 통과. `4.0.53` 빌드·타입 검사 통과, 린트 오류 0개·기존 경고 82개.
- 로컬 `4.0.53`의 전화번호 브라우저 8개, 부모님 성함 브라우저 12개
  시나리오 통과. 가상 API를 사용하며 운영 학생 자료를 변경하지 않는다.
- 소스 계약 10개, 프론트 매니페스트 7개, 백엔드 매니페스트 9개,
  운영 문서 21개 점검 통과. 변경 런타임 9개가 각각 500줄 이하다.
- 운영 코드 9개의 기준 체크섬이 후보의 기준과 일치했다. Vultr의 활성
  cron과 systemd 목록에서 폐기된 N100의 입력 동기화 작업은 발견되지 않았다.
- 서버의 제한된 위치에 학생 테이블 및 기존 런타임 7개를 백업했다.
  gzip 무결성·SHA-256을 확인하고, 학생 백업을 이름이 고유한 임시 DB에
  복원해 1,928명 전체 기존 데이터와 대표 번호의 SHA-256이 일치함을 검증했다.
  검증용 DB만 제거했고 운영 백업은 보존했다.
- `father_phone`, `mother_phone`을 nullable `VARCHAR(512) DEFAULT NULL`로
  INSTANT 추가했다. 전후 학생 수와 전체 기존 데이터·대표 번호 해시가 같다.
- 백엔드 9개 파일 적용 후 체크섬 일치, PACA 프로세스 1개, 스케줄러
  12개 모듈의 초기화, 운영 암호화 왕복, 실제 학생 상세 GET의 새 필드,
  미인증 401을 확인했다. 학생 자료를 테스트 값으로 수정하지 않았다.
- 공개 `/paca-health` 200 및 `https://pacapro.vercel.app`의 CORS 허용을 확인했다.

기존 전체 전환 감사의 Phase 1은 PACA·PEAK·다른 서비스 9개 환경 증빙의
갱신 조건 때문에 실패한다. Orchestration도 다른 서비스의 전환, 오래된
증빙 및 기존 전체 전환용 작업 분류 조건을 모두 충족하지 않는다.
이 감사들을 통과했다고 기록하지 않는다. 이번 배포는 원본 호스트·DB 소유권,
환경·인증·스케줄러·라우팅을 바꾸지 않는, 명시적으로 승인된 컬럼 두 개
추가에 한정하며 전용 점검으로 백업·무손실·호환성과 롤백을 검증한다.

## 적용 및 복구 순서

1. 운영 원본과 Git/Vercel 연결, 기준 코드, 암호화 설정을 확인한다.
2. 학생 테이블과 변경 코드를 백업하고 임시 DB 복원으로 백업을 검증한다.
3. 새 열의 기존 정의를 검사한 뒤 추가 DDL을 적용하고 기존 데이터 보존을 확인한다.
4. 변경 런타임만 적용하고 체크섬·서비스·API·암호화·스케줄러·공개 CORS를 검증한다.
5. 백엔드 검증 후 후보를 커밋·푸시하고 이전 Git 기준의 롤백 태그도 보존한다.
6. 푸시 SHA와 같은 Vercel Production 배포의 READY 상태와 표시 버전,
   부모님 번호 입력·재진입·상세·태블릿 화면을 확인한다.

앱 복구는 코드 백업과 이전 프론트를 사용한다. 새 DB 열과 이미 저장된 번호는
유지하며, `.down.mysql`이나 운영 DB 전체 복원을 일반 앱 롤백으로 실행하지 않는다.

초기 제한 환경에서는 접속·쓰기·로컬 포트 실행이 차단돼 운영 작업을 하지
못했다. 사용자가 실행 권한을 변경한 뒤 위 검증과 운영 적용을 이어갔다.
