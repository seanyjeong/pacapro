# 휴원·퇴원 후 청구가 남는 원인 조사 — 2026-10-07

운영 서버와 DB를 읽기만 했으며 코드·학생·청구를 수정하거나 배포하지 않았다. 관련 운영 파일 5개의 SHA-256이 현재 조사 worktree와 일치함을 확인했다. 실제 요청 로그는 IP·브라우저·리퍼러를 보존하지 않고 요청 시각·경로·결과만 기록했다.

교육원2 학생17은 2026-10-02 16:53:28 KST에 웹 앱의 `POST /paca/students/17/withdraw`가 200으로 처리됐고, 학생의 updated_at도 같은 시각이다. 현재 퇴원일은10월2일이다. 이 학생의 MCP 퇴원·별도정산 명령/정산 감사행은 조회 결과0건이다. 운영의 해당 POST 경로는 학생 상태·퇴원일과 출결만 정리하며 기존 student_payments 청구를 처리하지 않는다. 프론트 학생 상세 화면 퇴원 버튼이 이 경로를 호출한다. 따라서 일반 학생 수정의 미납 삭제 동작과 퇴원 버튼 동작이 일치하지 않는다.

사용자는 이 학생의 남은 학원비를 직접 처리했다고 밝혔다. 현재 10월 청구는 없고 기존 납부완료 이력은 유지된다. 이미 삭제된10월 청구의 원금·삭제 시각은 현재 행과 감사기록만으로 복원되지 않으므로 추측하지 않는다. 현재 청구 상태를 다시 변경할 이유가 없다.

일반 학생 수정에서 재원→휴원으로 변경할 때 `adjustPausedPayment`는 실제 학원비 student_payments가 아니라 legacy payments를 조회·수정한다. 운영 paca에는 payments 테이블이 없고 이 helper는 예외를 기록한 뒤 null을 반환한다. 휴원 상태 저장은 완료되면서 학비 조정이 누락될 수 있는 오류 경로다. 전용 `/process-rest`는 올바른 student_payments를 사용해 시작월 첫 청구를 삭제/일할 조정하므로 두 휴원 경로가 서로 다르다.

MCP 퇴원은 선택 settlements만 정산하고 나머지는 보존하며, 남은 청구가 있으면 정산 또는 preserve 결정을 요구한다. 현재 MCP에는 휴원 작업이 없다. 미납 조회는 학생이 휴원·퇴원 상태여도 남은 청구 자체를 표시한다. 학생 상태만으로 모든 과거 청구를 지워서는 안 된다. 일반 수정의 퇴원 cleanup은 부분납 청구도 삭제 범위에 포함하므로 이를 그대로 다른 경로에 복제하면 납부 이력을 손상할 수 있다.

권장 수정 범위는 퇴원 버튼과 상태 변경에서 동일한 청구 정산을 원자적으로 수행하고, 휴원 경로의 잘못된 결제 테이블 참조와 실패 숨김을 제거하는 것이다. 취소·감액·이월·실제 환불 기록은 해당 청구·납부 이력을 보존하며 처리해야 한다. 이 문서는 원인 확인 결과이며 해당 수정은 아직 구현·배포하지 않았다.
