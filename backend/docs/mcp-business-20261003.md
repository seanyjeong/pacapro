# GPT PACA·PEAK MCP 업무 확장 — 2026-10-03

대상은 `https://paca-mcp.supermax.kr/mcp`다. 로컬 구현·검증 완료, 운영 미배포 상태다. MCP 릴리스 버전은 **0.2.0**이며 PACA 웹 프론트는 변경하지 않는다(4.0.56). 두 저장소의 `codex/mcp-business` 브랜치가 한 릴리스다.

## 지원 범위

PACA 한 연결에서 기존 PACA 38종과 PEAK 33종의 원본 자료를 조회한다. PACA resource는 `peak_student_records`, `peak_daily_plans` 등 `peak_` 별칭으로 PEAK에 접근한다. PEAK 연결도 기존 41종에서 71종으로 확대되며 PACA 자료는 `paca_` 별칭이다. 필드·교육원 조건·현재 PACA 학생 소속·공유 자료 조건은 기존 허용 목록을 재사용한다. 양쪽 연결의 변경 작업은 12종에서 **24종**으로 확대했다.

| 업무 | 지원 변경 |
|---|---|
| 학생 | 기본정보 등록/부분 수정, 퇴원, 퇴원·졸업 학생 재원 복귀 |
| 상담 | 상담 등록/메모 수정/예약 변경, 성적·실기·목표 대학 상담 기록 등록/부분 수정 |
| PACA 출결·수납 | 출결 정정 및 체험 잔여 횟수 반영, 수강료 납부와 수입 장부 기록 |
| 일정 | 기존 수업/행사/강사 근무 일정 부분 수정 |
| PEAK 실기 | 기록 등록/부분 수정/한 건 삭제, 종목 활성 상태·허용 범위 검사 |
| PEAK 훈련 | 일지 등록/컨디션·메모·온습도 부분 수정 |
| PEAK 계획 | 빈 계획 등록/설명 부분 수정, 운동 한 건 추가/제거/완료 여부 설정 |

조회 도구는 PACA 18개, PEAK 9개다. PACA에 `preview_student_withdraw`, `preview_student_reactivate`와 `peak_recent_records`, `peak_event_ranking`, `peak_student_progress`를 추가했다. 기존 일반 `preview_change`에도 24종 작업을 노출한다. 미리보기는 DB 업무 행을 변경하지 않으며, 원장이 영향 목록을 확인한 뒤 `confirm_change`를 호출해야 실제 반영된다.

휴원 복귀(휴원 정산), 시즌 등록·청구 생성, 청구 취소·환불, 급여 지급, 문자 발송, PEAK 반 배정·출결 변경·월말 시험 기록 입력은 아직 MCP 쓰기로 제공하지 않는다. ‘모든 화면 기능 완료’라는 의미는 아니며, 일반 업무 조회와 위 표의 변경까지 검증한 릴리스다.

## 퇴원·재원 복귀 정책

`student_withdraw`는 기존 `POST /paca/students/:id/withdraw` 전용 경로의 정책을 따른다. 일반 학생 상태 수정 경로의 미납 삭제 부작용을 호출하지 않는다.

- `withdrawal_date`는 필수이며 오늘(KST) 이하의 실제 날짜다. 예약 퇴원은 지원하지 않는다.
- 학생 상태를 즉시 `withdrawn`으로 바꾸고 퇴원일·사유를 기록한다.
- 과거 출결과 미래의 체크된 출결은 보존한다. 오늘 출결(체크 여부 무관)과 미래 미체크 예약만 정리한다. 삭제될 id·날짜·상태를 미리 보여준다.
- 청구/납부/수입/시즌 이력은 수정·삭제하지 않는다. 문자도 보내지 않는다.
- 학생 변경, 출결 정리, 멱등 이력 저장이 한 트랜잭션이다. 출결 정리 실패 시 학생 상태도 롤백한다.

`student_reactivate`는 퇴원·졸업 학생만 `active`로 되돌린다. 휴원·체험·대기·예비생 전환에 쓰지 않는다. 퇴원 이력과 기존 수강 설정을 보존하고 휴원 필드를 초기화한다. 잔여 체험 플래그는 기존 `prepareStudentTrialUpdate` 규칙에 따라 해제한다. 즉시 청구 생성·과거 출결 복원은 없으며 이후 청구는 기존 시즌/수강 설정을 따른다.

## PEAK 원본 변경과 원자성

PEAK 학생 id와 PACA 학생 id는 다르다. PEAK 변경은 PEAK id를 받고 현재 연결된 PACA 학생의 교육원·삭제 여부를 다시 검사한다. 강사 id는 PACA 강사 id이며 원장은 음수 PACA 사용자 id다. 다른 교육원·퇴직 강사·현재 PACA 소속이 바뀐 학생을 거부한다.

PEAK pool 연결을 사용해 PEAK 업무 행과 PEAK `max_engine_commands`를 같은 트랜잭션에 저장한다. PACA 원장 테이블과 PEAK 업무를 두 연결로 따로 커밋하지 않는다. `max_engine_academy_locks`의 upsert가 교육원별 확인을 직렬화하고, 원본 행/연결 학생/강사/종목을 잠근 뒤 미리보기 해시와 비교한다. `FOR SHARE`로 PACA 원본을 읽으며 PACA 행을 쓰지는 않는다.

동일 학생·종목·날짜의 기존 기록이나 동일 날짜·시간대·강사 계획은 생성에서 거부한다. 기록 부분 수정은 생략 필드를 보존한다. 완료는 토글 대신 명시적 boolean이므로 재시도에 상태가 뒤집히지 않는다. 계획 전체 운동 목록 교체는 제공하지 않는다.

## 검증

근거는 `mcp-business-20261003/verification.json`, `source-manifest.json`, 세 검증 로그에 저장했다.

- PACA 운영과 동일한 Node 18.19.1, 격리 MySQL 8.4.11/127.0.0.1:13320, 합성 자료만 사용: 영향 범위 8 suites/70 tests + 기존 퇴원/연동 회귀 별도 2 suites/37 tests 통과.
- MCP Node 22.20.0: 실제 loopback OAuth·MCP 프로토콜 13 tests 통과, skip 0. PACA/PEAK 두 제공자의 도구 목록·미리보기·동일 확인 재시도·계정 분리 검사.
- 핵심 신규 서비스·저장소 5개 파일: statements 96.19%, branches 88.27%, functions/lines 100%.
- 변경 JavaScript ESLint, MCP no-undef/no-unused-vars, 구문/양쪽 24종 명령 일치, diff 공백 검사 통과. TypeScript/프론트 변경이 없어 타입 검사·프론트 빌드는 대상이 아니다.
- HTTP 단위 테스트는 기존 ephemeral server에서 간헐적 400/ECONNRESET이 있었다. 두 DB 통합 테스트는 서버를 한번 바인딩해 유지하도록 수정했고, 기존 라우트 회귀는 별도 실행으로 통과했다. 실패를 숨기거나 업무 기대값을 완화하지 않았다.
- 운영은 읽기만 수행했다. 기존 변경 대상 12개 파일은 운영 소스와 기준 커밋 해시가 모두 일치하며 신규 PACA 경로 10개는 운영에 없음을 확인했다. DB 권한 조회로 기존 PEAK 연결에 필요한 쓰기 권한이 있음을 확인했다. 승인·비밀값·OAuth 저장소 설정을 변경하지 않았다.

## 승인 후 적용 계획

`max-engine/AGENTS.md` §2.3의 운영 읽기 제한과 §7-1의 운영 수정·배포 확인 규칙에 따라 이번 신규 릴리스는 운영 승인 전이다. 과거 별도 릴리스 배포 승인을 이 변경의 승인으로 기록하지 않는다.

1. 현재 소스 해시/신규 경로 부재를 manifest와 재대조한다. 다르면 즉시 중단하고 원인을 보고한다.
2. PACA 코드, PEAK DB, 양쪽 MCP 현재 릴리스·포인터와 OAuth DB를 백업한다. 환경 비밀값은 저장소에 복사하지 않는다.
3. PEAK DB에만 `migrations/20261003_peak_max_engine_commands.sql`을 적용한다. 신규 ledger·lock 테이블 2개 생성이며 학생/기록 행을 변경하지 않는다. 운영 기존 테이블이 있다면 구조를 먼저 대조한다.
4. PACA 후보 파일만 교체하고 `paca-failover.service`를 재시작한다. `paca.js`·기존 bridge·일반 화면 라우트·cron·프론트는 보존한다.
5. 운영 MCP 현재 릴리스에서 새 디렉터리를 만들고 MCP 후보 파일만 적용한다. Node 22 사용, OAuth DB/환경/키 보존, 포인터 교체 후 `paca-mcp.service`와 `peak-mcp.service`를 재시작한다.
6. 두 health와 API catalog, 인증된 실제 MCP 도구 목록 및 합성 값 미리보기만 검증한다. 실학생 퇴원·복귀·기록 입력은 배포 스모크에서 확인하지 않는다. GPT의 새 도구 노출까지 확인한 후 운영 완료로 보고한다.

롤백은 후보 코드·MCP 포인터를 이전으로 복원하고 서비스를 재시작한다. 신규 PEAK 테이블과 이미 반영된 업무/멱등 이력은 삭제하지 않는다. 기존 OAuth 연결을 초기화하지 않는다. 프론트 변경이 없으므로 Vercel 배포·PACA 프론트 버전업은 이 릴리스에 포함하지 않는다.
